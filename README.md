# Browser Toolbox

웹을 쓰는 동안 늘 켜 두는 Chrome 확장이다. 미디어 배속, YouTube, 자막, 탭, 페이지, ChatGPT 도구를 한곳에 모은다.

> **개발 중이다.** 지금 있는 기능은 아래 둘이다. 나머지 기능은 차례로 더한다.
>
> - **미디어 배속**: 영상 위에 지금 배속을 보인다(모든 층을 지나는 가장 작은 뼈대).
> - **대화 열·작성란 너비**(ChatGPT): chatgpt.com의 대화 열과 작성란의 최대 너비를 정한 값으로 바꾼다. 사이트가 화면 구조를 바꿔 그 요소를 찾지 못하면 그 기능만 멈추고 팝업에 "찾지 못함"을 보인다.

## 지원 환경

- Windows의 데스크톱 Chrome 150 이상(manifest의 `minimum_chrome_version`과 같다)
- 화면 문구는 한국어다.
- Chrome 웹 스토어에는 올리지 않는다. 직접 빌드하거나 릴리스의 ZIP을 받아 "압축 해제된 확장"으로 불러온다.

## 설치

1. 아래 "빌드"대로 `dist/`를 만들거나, 릴리스의 ZIP을 받아 풀고 체크섬(`.sha256`)을 확인한다.
2. Chrome에서 `chrome://extensions`를 열고 오른쪽 위의 "개발자 모드"를 켠다.
3. "압축 해제된 확장 프로그램을 로드합니다"를 누르고 `dist/`(또는 푼 폴더)를 고른다.

확장을 지우면 Chrome이 그 확장의 설정도 지운다.

## 빌드

[pnpm](https://pnpm.io/installation) 12가 있으면 된다. Node.js는 pnpm이 저장소에 적힌 판(`package.json`의 `devEngines`)을 받아 쓴다.

```bash
pnpm install
pnpm verify
```

- `pnpm install`은 의존성과 테스트용 Chromium을 저장소 안(`node_modules`)에 받는다. Windows의 경로 길이 제한(260자) 때문에 저장소는 짧은 경로(대략 100자 이하)에 둔다. 경로가 길면 테스트용 Chromium이 실행되지 않는다(`spawn UNKNOWN`).
- `pnpm verify`는 CI와 같은 검사 전체다: 타입 검사, 린트, 서식, 구조 규칙, 안 쓰는 코드, 단위·DOM 테스트, 빌드(`dist/`), 시험 빌드(`dist-fixture/`), 확장 전체 테스트(확장 화면의 자동 접근성 검사 포함), 배포 ZIP과 SHA-256(`artifacts/`).

| 명령                 | 하는 일                                                                                              |
| -------------------- | ---------------------------------------------------------------------------------------------------- |
| `pnpm build`         | `dist/`에 압축 해제된 확장을 만든다.                                                                 |
| `pnpm build:fixture` | 시험 빌드(`dist-fixture/`): 제품에 시험 기능(`tests/extension/`)을 더한 것. 확장 전체 테스트만 쓴다. |
| `pnpm check`         | 빌드 없이 빠르게 검사한다(타입, 린트, 서식, 구조, 안 쓰는 코드, 단위·DOM 테스트).                    |
| `pnpm test:e2e`      | 빌드한 확장을 Chromium에 올려 시험 페이지에서 확인한다.                                              |
| `pnpm package`       | `dist/`를 배포 ZIP과 체크섬으로 묶는다.                                                              |
| `pnpm generate`      | 기능을 더하거나 뺀 뒤 진입점별 등록 목록을 다시 만든다.                                              |
| `pnpm mutation`      | 핵심 로직에 돌연변이 테스트를 돌린다(느리다).                                                        |
| `pnpm measure`       | 성능 예산(페이지마다 더 드는 시간, 팝업이 뜨는 시간, 크기)을 잰다.                                   |

## 권한

| 권한                        | 쓰는 곳                                                                               |
| --------------------------- | ------------------------------------------------------------------------------------- |
| `storage`                   | 설정을 저장한다.                                                                      |
| `scripting`                 | 확장을 다시 로드하거나 갱신했을 때, 열린 탭에 남은 옛 스크립트에게 정리하라고 알린다. |
| `http://*/*`, `https://*/*` | 모든 페이지의 모든 프레임에 있는 영상에 작용한다.                                     |

확장은 스스로 외부 서버에 데이터를 보내지 않는다.

## 문제 알리기

결함과 요청은 [GitHub Issues](https://github.com/dowoo108380/browser-toolbox/issues)에 양식으로 남긴다. 결함 양식은 Chrome 버전, 확장 버전, 사이트, 재현 절차를 묻는다. 이슈는 누구나 볼 수 있으므로 개인정보와 로그인한 화면의 내용은 넣지 않고, 사이트는 도메인만 적는다.

## 구조

```text
src/
  shared/      순수 도구(결과 값, 오류 종류, 제한 시간이 있는 기다림)
  contracts/   메시지 정의, 기능 정의의 타입
  platform/    chrome.* API를 감싸는 경계와 테스트용 가짜
  storage/     설정 저장 형식, 형식 이전, 설정 읽기 도우미
  dom/         웹 페이지 위 화면 틀(닫힌 shadow root), 페이지 스타일, 자원 범위, 외부 화면 요소 찾기
  sites/       외부 사이트(chatgpt.com)의 화면 지식: 요소를 찾는 선택자, 화면마다 있어야 할 요소, 사이트 안 이동 신호
  page/        콘텐츠 스크립트 실행 틀
  background/  서비스 워커(메시지 라우터, 설정 쓰기, 문제 기록)
  ui/          확장 화면(Preact)
  features/    기능 하나 = 폴더 하나, features/list.ts가 기능 목록
  entries/     진입점(서비스 워커, 팝업, 콘텐츠 스크립트)
scripts/       빌드, 등록 목록 생성, 패키징
tests/         확장 전체 테스트(e2e), 실제 모듈끼리 연결한 시험(integration), 시험 페이지, 설정 표본(samples), 시험 빌드의 시험 기능(extension)
```

- 위 목록에서 아래에 있는 층이 위에 있는 기반 층을 가져다 쓴다. 거꾸로는 쓰지 않는다. 예: `contracts` → `shared`, `storage` → `shared`·`contracts`·`platform`, `page`·`background`·`ui` → `storage`, `entries` → 모두. 위의 층을 모두 쓰는 것은 아니다(`dom`은 `shared`만, `sites`는 `shared`·`dom`만 쓴다). 기능끼리는 서로 가져오지 않는다. 규칙은 `.dependency-cruiser.json`에 있고 `pnpm verify`가 검사한다.
- 설정은 `chrome.storage.local`의 `settings` 키 하나에 둔다. 쓰는 곳은 서비스 워커 하나다. 사이트마다 정하는 설정(사이트 규칙, 사이트 예외)은 `sites[호스트][기능 id]`에 두고, 값의 모양은 그 기능이 정한다.
- 저장소의 값, 메시지, 백업처럼 신뢰 경계를 지나는 값은 `contracts`의 스키마 어휘 `v`로 검증한다(`v.object(...)`, `v.safeParse(schema, value)`). 그 안은 valibot이고, valibot을 가져오는 곳은 `src/contracts/schema.ts` 하나다. 다른 검증 라이브러리는 쓰지 않는다(린터가 막는다). 그 파일은 앞의 판(zod)과 받아들이는 값이 같도록 객체·기록 자리의 배열을 거절하고 글자 수를 코드 포인트로 센다. 받아들이는 값이 바뀌면 같은 형식의 옛 판과 새 판이 서로의 값을 다르게 읽으므로 `tests/integration/schema-acceptance.test.ts`의 표가 지킨다.
- 외부 사이트의 화면 구조에 기대는 기능은 그 요소를 이름 붙은 요소(`id`, 사람이 알아볼 이름, 찾는 함수)로 정의하고, 페이지 쪽 시작 함수가 받는 `find`로 찾는다. 찾기 시작한 때부터 탭이 보인 시간이 15초가 되도록 찾지 못하면 실행 틀이 그 기능만 멈춰 그 기능의 변경을 모두 되돌리고, 문제 기록에 그 요소를 남기며, 팝업의 그 기능에 "찾지 못함: (요소 이름)"을 보인다. 그 요소가 나중에 나타나면 기능을 다시 시작한다. 요소를 찾는 방법(선택자, 문구)은 그 사이트의 모듈(`src/sites/<사이트>/`) 한 곳에만 둔다. 사이트의 모양만 바꾸는 기능(ChatGPT 너비)은 사이트 모듈이 준 선택자로 페이지에 스타일 요소 하나를 넣는다. 사이트가 요소를 다시 그려도 새 요소에 그대로 걸리므로 찾은 요소를 따라가지 않고, 찾기는 그 화면에 있어야 할 요소가 없어졌는지 알아채는 데만 쓴다.
- 기능 정의의 `content`는 그 기능이 페이지에 작용하는 곳이다. 빌드는 `sites`로 그 기능의 페이지 쪽 일을 넣을 콘텐츠 스크립트 묶음을 고르고, 묶음은 모든 프레임에 실린다(미디어 기능은 iframe 안의 영상에도 작용한다). `sites`가 `'all'`이면 모든 묶음에, 사이트 이름(`src/contracts/feature.ts`의 `sites`, 지금은 `chatgpt`)이면 그 사이트의 묶음(`content-<사이트>.js`)에만 든다. 사이트 묶음은 모든 사이트의 기능도 함께 담고 공통 묶음(`content-common.js`)은 그 사이트에 실리지 않아, 한 프레임에 실리는 묶음과 실행 틀은 늘 하나다. 팝업은 사이트 전용 기능을 다른 사이트의 탭에서 열면 그 사이트에서만 쓸 수 있다고 보인다. `frames: 'top'`인 기능은 실행 틀이 탭의 최상위 프레임에서만 시작한다. 페이지에 작용하지 않는 기능(`content: null`)에는 페이지 쪽 일을 만들 수 없다(타입 검사가 막는다).
- 콘텐츠 스크립트는 기능 목록을 싣지 않는다. 등록 목록의 페이지 쪽 일(`definePagePart`)이 그 기능의 정의를 싣고, 설정 읽기는 그 정의들의 항목만 검증한다. 다른 기능의 항목은 모르는 기능의 것처럼 보지 않는다. 그래서 페이지에 작용하지 않는 기능이 늘어도 모든 페이지에 드는 비용은 늘지 않는다. 의존 규칙(`page-scripts-own-features`)과 `tests/e2e/page-bundle.spec.ts`가 지킨다.
- 실행 기능의 작업 기록은 `chrome.storage.session`의 `tasks` 키에 탭마다 하나 둔다. 쓰는 곳은 서비스 워커 하나이고, 확장을 다시 불러오거나 갱신하거나 브라우저를 다시 시작하면 빈다(그래서 형식 버전이 없다). 확장 아이콘의 탭마다 배지와 제목은 이 기록에서 계산한다.
- `tests/samples/settings/`에는 낸 판마다 그 판이 `settings`에 실제로 쓴 값을 하나씩 둔다(파일 이름은 그 판의 manifest 버전). 낸 판의 표본은 고치지 않는다. 모든 표본을 지금 판이 손상 없이, 저장된 항목과 필드를 하나도 잃지 않고 읽어야 한다(`tests/integration/settings-samples.test.ts`).
- 같은 형식 버전이면 옛 판과 새 판이 서로의 값을 읽을 수 있어야 한다. 어느 판이든 같은 형식에서 자기 스키마가 거절하는 항목은 손상으로 보고 그 항목 전체를 기본값으로 고쳐 쓰기 때문이다. 그래서 같은 형식 버전 안에서 할 수 있는 변경은 기능 설정 항목(기능 하나의 설정, 사이트 하나에서 기능 하나의 설정)의 최상위에 기본값 있는 필드를 더하기, 기능을 더하기, 사이트 설정이 없던 기능에 사이트 설정을 더하기뿐이다. 옛 판이 거절할 값을 새로 저장하게 되는 변경(이미 있는 필드가 받는 범위를 넓히기. 예: 1–2를 1–3으로, 고를 수 있는 값을 더하기, 빈 값이나 다른 타입을 받기)과 옛 판이 저장한 값을 새 판이 거절하거나 다르게 읽게 되는 변경(필드를 빼거나 이름을 바꾸기, 받는 범위를 좁히기, 저장된 값을 다르게 읽기, 기능 id를 바꾸거나 기능을 지우기, 사이트 설정을 정한 기능에서 그것을 빼기)은 형식 버전을 올리고 이전 함수를 둔다. 설정 자체의 최상위 구조(`version`, `revision`, `features`, `sites`)에 키를 더하는 것도 형식 버전을 올린다. 옛 판은 지금 구조로 검사한 값을 바탕으로 쓰므로 모르는 최상위 키를 지운다. 이 목록으로 가를 수 없으면 형식 버전을 올린다. 형식 버전이 더 새면 옛 판은 기능을 시작하지 않고 그 설정을 읽지도 고쳐 쓰지도 않으므로 값을 잃지 않는다. 범위를 넓혔는지와 필드를 항목의 최상위에만 더했는지는 시험이 알 수 없어(지금 코드에는 옛 판의 스키마가 없다) 검토에서 본다.
- 새 판을 쓰다 옛 판으로 되돌려도 새 판이 더한 필드를 잃지 않아야 한다. 그래서 설정을 쓰는 곳은 스키마를 거친 값이 아니라 저장된 항목 위에 검증을 거친 값을 덮어 쓰고, 이 판이 모르는 항목과 필드는 그대로 둔다(`tests/integration/settings-newer-fields.test.ts`). 이 판의 화면이 보낸 요청에 든 모르는 필드는 저장하지 않는다(스키마가 거른다). 저장하면 뒤의 판이 같은 이름의 필드를 더할 때 그 값을 다르게 읽는다. 기능 설정과 사이트 설정의 스키마는 모르는 필드를 거절하지 않게 `v.object`로 쓰고(모르는 필드를 거절하는 strictObject가 아님), 필드는 항목의 최상위에만 더한다. 안쪽 객체나 배열 원소에 더한 필드는 옛 판이 그 항목을 바꿀 때 지워진다.
- 웹 페이지의 문맥에서 도는 코드(콘텐츠 스크립트, `chrome.scripting.executeScript`로 넣는 함수)는 보안 문맥에서만 있는 웹 API(예: `crypto.randomUUID`)를 쓰지 않는다. 일반 http 페이지에는 없다. 필요한 값은 서비스 워커가 만들어 넘긴다. 확장 전체 테스트의 시험 페이지는 보안 문맥인 `127.0.0.1`과 보안 문맥이 아닌 `insecure.test`(시험 브라우저가 루프백에 이음) 두 출처로 열 수 있고, 주소 앞에 `/loading/`을 붙이면 시험 서버가 응답을 끝내지 않아 로딩이 끝나지 않는 문서가 된다.
- 실행 코드는 시험에서도 문자열로 쓰지 않는다. 페이지나 서비스 워커에서 돌릴 코드는 타입 검사를 받는 함수로 쓰고 Playwright의 `evaluate`에 함수로 넘긴다. 스크립트 요소 만들기와 평가 함수에 문자열 넘기기는 린터가 막는다.
- `chrome.scripting.executeScript`는 기본으로 문서가 다 실릴 때까지 기다린다. 기다릴 이유가 없는 함수는 `injectImmediately`로 넣고, 모든 기다림에는 제한 시간을 둔다(`src/shared/timeout.ts`).
- 저장된 설정을 읽을 수 없어 기본값으로 고쳐 쓰면, 서비스 워커가 무엇을 바꿨는지 `repairNotice` 키에 먼저 남기고 팝업이 사용자가 확인할 때까지 보인다.
